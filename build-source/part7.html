Cómo funciona Sentry

How Sentry works

Sentry recibe los errores y las mediciones de rendimiento de la app. Se usa el mismo código para web y nativo, pero con el SDK que corresponde.

Sentry receives the app's errors and performance measurements. The same code serves web and native, but with the matching SDK.

  1. Dos SDK, un nombre. Sentry es @sentry/react en web y @sentry/react-native en nativo ({{C:src/utils/sentry.ts:19}}). En nativo se agrega además la integración con React Navigation ({{C:src/utils/sentry.ts:26}}).
  2. Se inicia al arrancar. initializeSentrySdk ({{C:src/utils/sentry.ts:88}}) se llama al principio de la App ({{C:src/App.tsx:203}}). Configura el DSN, el ambiente ({{C:src/utils/sentry.ts:132}}: en web, "Store" o "Beta" según el dominio) y una lista de errores ignorados ({{C:src/utils/sentry.ts:41}}).
  3. Cuántos eventos se muestrean. En producción se envía 1 de cada 10 trazas y también 1 de cada 10 errores; en desarrollo, todo ({{C:src/utils/sentry.ts:46}}). El porcentaje de errores es fijo; los de trazas y perfiles se pueden cambiar. Cuando Flagsmith está listo, refreshSentrySampleRatesFromFlagsmith ({{C:src/utils/sentry.ts:70}}, llamada desde {{C:src/utils/FeatureProvider.tsx:124}}) guarda los porcentajes nuevos, y el muestreador los usa en la siguiente transacción ({{C:src/utils/sentry.ts:106}}). Estos dos se pueden subir o bajar sin publicar una versión.
  4. Etiquetas útiles. Cada evento lleva el tipo de TV, la versión del contenedor y del sistema ({{C:src/utils/sentry.ts:110}}, llamada en {{C:src/App.tsx:261}}), el id del dispositivo ({{C:src/utils/sentry.ts:120}}, en {{C:src/App.tsx:275}}) y la versión de red IPv4/IPv6.
  5. Los errores pasan por el LogManager. El código no llama a Sentry directamente: usa LogManager, que registra un SentryProvider ({{C:src/managers/LogManager/LogManager.ts:69}}). Ese proveedor convierte el error a un formato válido, le agrega contexto, huella y la etiqueta de dominio, y llama a captureException ({{C:src/managers/LogManager/providers/SentryProvider.ts:69}}). Los niveles de la app se traducen a niveles de Sentry ({{C:src/managers/LogManager/providers/SentryProvider.ts:43}}), y los mensajes informativos se guardan como migas de pan (breadcrumbs) ({{C:src/managers/LogManager/providers/SentryProvider.ts:77}}).
  6. Red de seguridad en la interfaz. Un ErrorBoundary envuelve la app en nativo ({{C:src/App.tsx:319}}) y en web ({{C:src/App.web.tsx:365}}); si algo se rompe al dibujar, muestra una pantalla de error con el id del evento. En nativo, además, toda la App se envuelve con Sentry.wrap ({{C:src/App.tsx:341}}).
  7. Rendimiento. SentryPerformanceProvider ({{C:src/managers/LogManager/providers/SentryPerformanceProvider.ts:10}}) es el que usa PerformanceTracker para medir tramos como la carga de SDKs.
  1. Two SDKs, one name. Sentry is @sentry/react on web and @sentry/react-native on native ({{C:src/utils/sentry.ts:19}}). On native the React Navigation integration is added too ({{C:src/utils/sentry.ts:26}}).
  2. It starts at launch. initializeSentrySdk ({{C:src/utils/sentry.ts:88}}) is called early in App ({{C:src/App.tsx:203}}). It sets the DSN, the environment ({{C:src/utils/sentry.ts:132}}: on web, "Store" or "Beta" depending on the domain) and a list of ignored errors ({{C:src/utils/sentry.ts:41}}).
  3. How many events are sampled. In production 1 in 10 traces and also 1 in 10 errors are sent; in development, everything ({{C:src/utils/sentry.ts:46}}). The error rate is fixed; the trace and profile rates can be changed. Once Flagsmith is ready, refreshSentrySampleRatesFromFlagsmith ({{C:src/utils/sentry.ts:70}}, called from {{C:src/utils/FeatureProvider.tsx:124}}) stores the new percentages, and the sampler uses them on the next transaction ({{C:src/utils/sentry.ts:106}}). These two can be raised or lowered without shipping a release.
  4. Useful tags. Every event carries the TV type, container and OS versions ({{C:src/utils/sentry.ts:110}}, called at {{C:src/App.tsx:261}}), the device id ({{C:src/utils/sentry.ts:120}}, at {{C:src/App.tsx:275}}) and the IPv4/IPv6 network version.
  5. Errors go through the LogManager. Code does not call Sentry directly: it uses LogManager, which registers a SentryProvider ({{C:src/managers/LogManager/LogManager.ts:69}}). That provider turns the error into a valid format, adds context, fingerprint and the domain tag, and calls captureException ({{C:src/managers/LogManager/providers/SentryProvider.ts:69}}). App log levels map to Sentry levels ({{C:src/managers/LogManager/providers/SentryProvider.ts:43}}), and informational messages are kept as breadcrumbs ({{C:src/managers/LogManager/providers/SentryProvider.ts:77}}).
  6. A safety net in the UI. An ErrorBoundary wraps the app on native ({{C:src/App.tsx:319}}) and web ({{C:src/App.web.tsx:365}}); if rendering breaks it shows an error screen with the event id. On native the whole App is also wrapped with Sentry.wrap ({{C:src/App.tsx:341}}).
  7. Performance. SentryPerformanceProvider ({{C:src/managers/LogManager/providers/SentryPerformanceProvider.ts:10}}) is what PerformanceTracker uses to time spans such as SDK loading.
